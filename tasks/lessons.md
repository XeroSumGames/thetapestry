# Lessons Learned

## PostgREST embedded joins require FK to public.profiles, not auth.users (2026-06-23)

`pregen_library.author_id` pointed to `auth.users(id)`. The Supabase data layer called `.select('*, profiles!pregen_library_author_id_fkey(username)')`. This produced PGRST200: "Could not find a relationship between 'pregen_library' and 'profiles' in the schema cache." at the story lobby - discovered in the 2026-06-23 playtest logs.

Root cause: PostgREST resolves embedded joins exclusively through public-schema FKs. `auth.users` is a private schema; even though `profiles.id` references `auth.users.id` via CASCADE, a FK that points DIRECTLY to `auth.users` is invisible to the join resolver.

**Rule:** Any table column that will be used in an embedded join with `.select('*, profiles!fk_name(col)')` MUST have its FK pointing to `public.profiles(id)`, not `auth.users(id)`. Cascade semantics are preserved: `profiles.id` cascades from `auth.users`, so SET NULL on the child still fires correctly when the user is deleted. Fix: drop + recreate the FK targeting `public.profiles`. Also run `NOTIFY pgrst, 'reload schema'` after DDL changes to flush the PostgREST schema cache without waiting for the next connection. Fixed in `sql/fix-pregen-author-fkey.sql`, commit `47380523`.

## A feature flag honored at ONE surface is not "wired" - trace it through every landing point (2026-06-22)

Observer mode (`campaign_members.observer`) was correctly respected at the table (player-bar filter, combat-slot filter, presence) but the JOIN flow dropped observers at the player **lobby**, which had zero `observer` branch - so an observer saw the full "pick a survivor" onboarding instead of watching silently. Two compounding gaps: (1) the join page redirected observers to `/stories/[id]` (lobby) instead of `/stories/[id]/table`; (2) the 23505 "already a member" branch did a no-op insert that silently dropped the observer flag, so an existing member who followed the observer link never actually became one.

**Rule:** when a boolean/role flag changes behavior, grep every surface the user can reach (`/join`, lobby, table, any redirect target) and confirm each one reads the flag. "Handled at the table" is necessary, not sufficient. ON-CONFLICT inserts (`23505`) drop the conflicting row's columns - if intent must persist, follow with an explicit UPDATE. Fixed in `app/stories/join/page.tsx` + `app/stories/[id]/page.tsx`.

## Arch ratchet: force-rebaseline is correct for intentional god-component growth (2026-06-18)

When adding a legitimate new feature section to a god-component (like the Pregens queue in `moderate/page.tsx`), the `--force` flag on `check-arch.mjs --save --force` is the correct tool. `--save` alone refuses to raise LOC ceilings; `--force` re-baselines the exact current values. ## Windows sed introduces UTF-8 BOM - always strip after mass sed sweeps (2026-06-18)

`sed -i` on Windows (Git Bash / WSL interop) rewrites files with a UTF-8 BOM (`\xEF\xBB\xBF`) prepended. Turbopack hard-fails on BOM in CSS (`Parsing CSS source code failed`); Next.js TSX compilation also chokes. The symptom is a Vercel deploy failure on `app/globals.css:1:2` showing `﻿@font-face`.

**Rule:** After ANY `sed -i` mass-replace across source files on Windows, immediately run the BOM scan + strip before committing:

```python
import glob
patterns = ['app/**/*.tsx','app/**/*.ts','app/**/*.css','components/**/*.tsx','lib/**/*.ts','lib/**/*.tsx']
for pat in patterns:
    for path in glob.glob(pat, recursive=True):
        with open(path,'rb') as f: data=f.read()
        if data[:3]==b'\xef\xbb\xbf':
            with open(path,'wb') as f: f.write(data[3:])
```

Alternative: use Python for mass-replace entirely (reads/writes in binary, no BOM added) instead of sed. The sed approach is fragile on Windows even in Git Bash.

## Multi-phase charge cancel: each fix only addressed one sub-path, three commits to fully close (2026-06-18)

The charge cancel bug took three commits to fully close because it had three distinct failure modes. Fix 1 (`550e252`): "Cancel Move" button wasn't calling `handleMapMoveCancel`. Fix 2 (`6d86456`): `pendingChargeRef` survived the cancel due to a React state-timing edge case - `handleMapMoveComplete` was firing on the subsequent regular Move and triggering the roll modal. ## When a shipped fix doesn't fully resolve a bug, add a defensive secondary guard (2026-06-17)

The charge cancel bug was marked [FIXED 550e252] but recurred in Session 24. Dump analysis revealed that `handleMapMoveCancel()` was being called correctly (clearing pendingChargeRef), but the charge modal still fired on the next regular Move click - a React state-timing edge case where `pendingChargeRef` survived the cancel. ## A schema value of 0 for a percentage-multiplied field produces 0 output (2026-06-17)

`damageBase: 0` with `rpPercent: 400` gives 0 RP (0 x 400% = 0). If a weapon needs to deal a fixed non-zero RP with 0 lethal output, use `damageBase: 1` as a technical minimum to drive the percentage math, relying on the runtime isStun check to zero the finalWP. The `damageBase: 1` is never visible to the player since the stun zeroing fires before output. Alternatively, add a `flatRP` field to the schema for true "0 WP / N RP" semantics - but that requires schema + calculateDamage changes and should be done when multiple weapons need it.

## React stale-closure on async DB writes: always fetch fresh state inside mutation handlers (2026-06-11)

`handleClone` in `NpcRoster.tsx` captured `npc.name` and `npcs` from the render closure. ## A useEffect-driven persist effect can never beat a tight bus inbound + setTimeout(0) suppress flag race; bind persist to the explicit user action instead (2026-05-30)

The scene-controls popout's `cellPx` persist effect had `[cellPx, scene?.id, supabase]` deps + a `suppressOutboundRef` flag set true around bus inbound. The flag was lifted in `setTimeout(suppress=false, 0)` (a macrotask), but React's effect flush timing is variable - non-user `cellPx` changes (bus inbound from main window, hydration from `load()`, scene-id changes) occasionally beat the suppress and wrote a stale value to the wrong scene. After the 2026-05-30 playtest where `cell_px=200` reappeared *minutes* after a fresh DB reset across multiple hard refreshes, the fix was structural: removed the persist `useEffect` entirely and bound persist directly to the stepper's `onChange` callback. Now only an actual user click on +/- writes to the DB - bus / hydration / scene-id changes update local state without touching persistence. ## When setZoom and a DOM operation must use the same value in the same tick, the DOM op must use EXPECTED dimensions, not stale DOM state (2026-05-29)

Fix: compute expected canvas dims directly from `Math.max(container.clientWidth, grid_cols * cellPx * scale)` (matching `draw()`'s own formula) and pass them to the centering math. General rule: any time you call `setState(newValue)` and immediately need a DOM dimension that DEPENDS on that state, derive it from the new value - never read it back from the DOM which reflects the old state.

## Multi-lane push escape: cherry-pick into a detached worktree, then `reset --mixed` (2026-05-24, validated)

When the main checkout is too cluttered with the OTHER lane's untracked files to `git pull --rebase` (rebase does a checkout and dies on "untracked working tree files would be overwritten" - e.g. a leftover untracked `e2e/*.spec.ts` the other lane has since committed), do NOT delete their files or `--no-verify`. The reliable escape (used successfully this session to land Phase 2):
1. `git worktree add --detach .claude/worktrees/pushwt origin/main` (clean tree, no untracked junk -> ratchet green, no collision).
2. In it: `git cherry-pick <your-local-sha>` then `git push origin HEAD:main`. (Cherry-pick is clean when your diff doesn't overlap the other lane's commit.)
3. Back in the main checkout: `git fetch origin main` then `git reset --mixed origin/main` - moves the branch pointer to the new main WITHOUT touching the working tree, so the other lane's uncommitted work is preserved and your now-pushed files show as clean.
4. Clean up: you must `cd` OUT of the worktree first (Windows holds a lock on the cwd -> "Permission denied"); then `git worktree remove ... --force`, `git worktree prune`, and `rm -rf` the dir if it lingers.

## God-component function extraction: byte-exact script move + destructure-deps + tsc convergence (2026-05-23)

**Technique** for lifting a huge function (here: the ~1810-line `executeRoll`) out of a god-component into a hook/module WITHOUT risking a silent behavior change. Reused for every Phase 5 god-component extraction.

1. **Find exact boundaries** (`grep -n` the function + its neighbor). Confirm the closing brace line.
2. **Slice the body with a script** (node `readFileSync().split(eol).slice(start,end)`), do NOT retype it. Retyping 1800 lines from context WILL drift. **Detect CRLF vs LF** and split/join on the actual EOL - Windows files are `\r\n`, and `split('\n')` leaves a `\r` on every line that breaks all string matching.
3. **Move the body VERBATIM** into `useX(deps) { const {...} = deps; <BODY>; return { fn } }`. Destructure every dependency at the top so the body text is unchanged (no `deps.` prefixing - that's 40+ error-prone edits). The page destructures the fn back out; call sites stay unchanged. Same pattern as `useGmTools`.
4. **Derive the deps set mechanically, not by eye:** tokenize the body, intersect with the component's declared identifiers (useState/useRef/function/const at 2-space indent) = deps; intersect with the import block = needed imports. BUT the tokenizer also catches comment mentions and string-literal keys (e.g. `groupCheckParticipants:` as an object key, or a name in a `//` comment) - so **grep the body for each candidate's real CODE usage** before trusting it. Over-inclusion is safe (unused destructure, no `noUnusedLocals`); under-inclusion is caught by tsc.
5. **tsc is the completeness oracle, both directions:** a missing dep -> "Cannot find name X" inside the hook; a spurious dep -> "Cannot find name X" at the call-site object. Iterate to clean. Watch for TDZ: any dep declared AFTER the extracted function must be hoisted to the call site (here: `syncedSelectedEntry`) - it was a hoisted `function` before (always available) but a hook CALL runs in place.
6. **PROVE behavior preservation:** diff the extracted body against the git-HEAD original (`git show HEAD:file | slice`) after CRLF-normalizing - assert byte-identical. Then assert the hook file `.includes()` that body verbatim. Only then is "behavior-preserving" a fact, not a hope.
7. **Type the deps interface from source:** copy inline state types verbatim (e.g. the `mapTokens` shape), refs as `MutableRefObject<T>`, setters as `Dispatch<SetStateAction<T>>`, `supabase` as `ReturnType<typeof createClient>`. If a function's real return type bites (saveRollToLog returns `{total,outcome,insightAwarded}` not void) and the body ignores it, type the return precisely or `any`-the-ignored-field. Note the dual `RollResult` (./types interface vs lib/roll-outcomes union) - disambiguate.
8. **Do NOT also refactor** (pure/effect split, dedup, rename) in the same commit. Relocation-only keeps a 2-client / smoke failure localizable to "the move," not "the move plus 5 changes."

## Deleting a local var that shares a name with component state = silent rebind, not a compile error you'd expect (2026-05-23)

**Rule:** Before deleting a `let`/`const` local, grep the enclosing function for an outer-scope binding of the SAME name. If one exists, every reference to the local silently rebinds to the outer one instead of erroring "undefined."

**What it caught (3c-B1):** `executeRoll` had local `let distractResult = ''` / `let stabilizeResult = ''` (dead branches being removed), but the component ALSO has state vars `distractResult` / `stabilizeResult` (type `SharedRollResult | null`, for the dedicated modals). The `traitNotes` array spread `...(stabilizeResult ? [stabilizeResult] : [])` read the locals. Deleting just the branches (not the spreads) would have left the spreads compiling fine - but now reading the COMPONENT STATE objects and pushing `SharedRollResult` into a `string[]`. tsc would have flagged the array-type mismatch here, but a same-typed shadow (string local shadowing a string state) would NOT - it'd silently change runtime behavior with a green build. The phase4-prestage commit knew this and removed the spreads too; I verified and matched.

**Detection:** when removing a local, search the whole component for the identifier. Adjacent surviving references to a now-removed local are a rebind risk, not a guaranteed compile failure. This is why behavior-preserving deletions need the grep, not just "tsc passed."

## Reading image-only PDF tables: PyMuPDF render -> PNG -> vision (2026-05-20)

**Technique.** The Quickstart + CRB rulebook tables are images with no text layer (`pdftotext` / Grep on the `.txt` returns nothing; `page.search_for()` returns empty). The PDF Read tool also fails (`pdftoppm` not on PATH). Working path:

```python
# py -c (Windows: the `py` launcher has fitz; bare `python`/`python3` do not)
import fitz
doc = fitz.open(r'docs/Rules/<file>.pdf')
pg = doc[PAGE_INDEX]              # 0-indexed
clip = fitz.Rect(x0, y0, x1, y1) # crop to the table region (fractions of page rect)
pix = pg.get_pixmap(matrix=fitz.Matrix(7,7), clip=clip)  # 7x zoom for legibility
pix.save(r'.claude/tmp-x/out.png')
```

Then Read the PNG (vision). Iterate the clip rect + zoom until the table is crisp. Clean up the temp PNGs after (`rm -rf .claude/tmp-x`). On Windows use the `py` launcher, not `python` (the bare alias routes to the Microsoft Store stub). This is how the explosives audit (Table 13) got read.

## Never combine `git stash push <file>` with rebase --autostash (2026-05-19)

**Banned workflow.** Cost ~30 min today + a silent missing-fixes ship (`d5fd410`).

```sh

git stash push supabase/.temp/cli-latest         # stash one specific file
git fetch + git -c rebase.autoStash=true rebase  # autostash kicks in
git commit -m "..."                              # commits stale state
```

What happened: the autostash flag tried to stash any UNSTAGED working-tree changes for the rebase. My specific-file stash plus the autostash dance silently UNSTAGED my 13 `git add` targets. ## "Latent stale-closure" suspicion on realtime hooks is usually inverted - the seam IS the fix (2026-05-24)

But the worktree was created 2 days earlier and origin/main had moved 111 commits ahead in that time. The bug fix I then proposed cited line numbers and code that didn't exist on the live deploy. Rule: state check must include `git log HEAD..origin/main --oneline` and report the count. If non-zero, rebase BEFORE proposing fixes - line numbers from a stale worktree are worse than no line numbers. Bonus signal: `git status` says "Your branch is behind origin/main by N commits" - read that line, don't skim past it.

## Handoffs go stale and wrong - derive state from git/disk at write time, distrust it at read time
- **A handoff is one chat's point-in-time belief, not ground truth. Treat its facts as hypotheses** (2026-05-21, Xero: "I hate how inaccurate your handoffs are between chats"). The puffer-fish handoff's resume pointer said "next untouched item is A5.5 (rate-limit audit)" - but `tasks/audit-rate-limit-coverage-2026-05-20.md` already existed (shipped the prior day). I caught it only because I Glob'd the API surface before writing. Two root causes: (1) memory-drift - the writing chat asserted "untouched" from belief without an `ls`/Glob file-existence check; (2) cross-lane staleness - the two lanes ship in parallel, so a claim true at write time is false by read time.
- **WRITE side - derive, don't recall.** When producing ANY handoff (chat block or `tasks/handoff.md` Session-State), every factual claim comes from a command run in the same turn: HEAD from `git rev-parse`, test count from `refresh-ledger.mjs`, "X shipped" from `git log | grep`, "Y is next / untouched / to-be-written" from Glob/`ls` (does it ALREADY exist?) + the todo's open/closed state. Stamp volatile claims "(verified @ <sha>)". A claim with no provenance is a guess.
- **READ side - hypothesis, not truth.** `sh scripts/start-session.sh` now reports per-state-file freshness (commits-behind-main for `handoff.md` + both lane plans). On the session that found this, it flagged `puffer-fish-platform-plan.md` as 28 commits behind - exactly the distrust signal that was missing. Before acting on a "what's next" claim, spot-verify against git log / Glob / todo.
- **Structural principle:** facts git/disk can answer in 2 seconds (HEAD, counts, shipped status, file existence) belong to the substrate, not frozen in handoff prose. The handoff's real payload is what the substrate CAN'T tell you - intent, judgment calls, why-this-order, gotchas. Same as the auto-memory rule: don't store what's derivable from current state. Full contract: `tasks/handoff.md` "Handoff accuracy contract".

## God-component extraction: the repeatable recipe + the discipline that kept breakage at zero
- **Context (2026-05-21/22 table re-arch):** Xero mandated migrating `app/stories/[id]/table/page.tsx` (13,565 lines) to the target architecture in one continuous push, break-things-OK, critical-testing-only. Took it to 12,565 (-1,000 total) with ZERO breakage. The 2026-05-22 window shipped 4 leaf extractions (RestorePicker, GrantAdvantage, FeedColumn, CommunityStatus = -417) and EXHAUSTED the clean-leaf supply: every remaining render region (Header, asset sidebar, portrait strip, initiative action region) and modal (Grapple, ReadyWeapon, SpecialCheck, Recruit, NPC-picker) is trunk-coupled (initiative / tactical / roll-engine / GM-tools-action-dispatch). The how matters more than the number:
- **The leaf-modal recipe (proven 6x):** (1) read the inline block + its state decls verbatim; (2) create `components/FooModal.tsx` (`'use client'`), copy the JSX + handler UNCHANGED; (3) thread state values/setters + supabase + channelRef + an `onX` callback as props - state stays in page.tsx for now, migrates to a hook (`useGmTools`) later; (4) import pure lib deps DIRECTLY in the component (triangleBreakdown, computeEncumbrance, advanceCampaignClock, exportSessionLog, restoreCampaignSnapshot) rather than threading them; (5) replace the page block with `<FooModal .../>`; (6) trim now-orphaned page imports; (7) `npx tsc --noEmit` is the gate. Hooks (`useRecorderToggle`) follow the same shape into `hooks/`.
- **Type the leaky props loosely.** `entries: any[]`, `setEntries: any`, `supabase: any`, `channelRef: { current: any }`. Importing the real page types invites variance friction (Dispatch contravariance on SetStateAction) that stalls the gate for zero behavior benefit. The component's field access is copied verbatim, so behavior is identical regardless.
- **Discipline = stop before context depth degrades transcription.** tsc catches structural errors (missing dep, wrong type) but NOT semantic transcription slips (copied `id` where you meant `campaignId`, wrong variable in a verbatim handler). Those errors scale with how deep the context window is. Rule: 1-2 extractions per window, then checkpoint. Stopping early on health/clock/state-mutating modals (AdvanceTime, then RestorePicker) is why the breakage count stayed at zero - not caution for its own sake. PROVEN AGAIN 2026-05-22: RestorePicker (the riskiest leaf - parallel per-row health UPDATEs, optimistic patches across 4 state slices, background refetch+broadcast) was deferred from the prior window precisely so it could be done FIRST with fresh context. Doing it alone, then committing/pushing/checkpointing before touching the trunk-tangled render regions, kept breakage at zero. The discipline applies to the SECOND extraction too: when the next item is a large structural region (the ~1,800-line GM sidebar / initiative strip / tactical region), it is itself a "do-first-with-fresh-context" item, NOT a tail-of-window grab - those regions thread the initiative + tactical + realtime trunk state machines (Step 3a/3b), so they are not clean leaves.
- **Reclassify "leaf" candidates that call trunk systems.** ReadyWeapon LOOKED like an easy modal but calls `consumeAction` / `clearAimIfActive` (initiative). A modal that touches a trunk state machine extracts WITH that machine's hook (Step 3b), not as a standalone leaf - otherwise you thread combat plumbing as throwaway props. Grep a modal's handler for trunk-system calls before classifying it.
- **Grep usage-count before trimming a "now-orphaned" import.** Burned once: trimmed `writeCampaignEnabled` assuming the extracted modal was its only consumer; the realtime broadcast handlers still used it (tsc TS2304 caught it). Same with `restoreCampaignSnapshot` (RestorePicker still uses it after ReloadPicker left). `grep -c <symbol> page.tsx` first: count 1 = import-only = safe to trim; >1 = keep. Note the trap: `count 2` can be import + a COMMENT mention (it bit the FeedColumn trim - `ChatMessageList`/`ChatComposer` showed count 2 but the second hit was a `// <ChatComposer>...` comment, not real usage). When count is 2, eyeball the non-import line to confirm it's actual code before deciding keep-vs-trim.
- **The clean-leaf supply is finite; know when it's exhausted (2026-05-22).** After the four 2026-05-22 leaf extractions, EVERY remaining unit in `table/page.tsx` is trunk-coupled. The tell: grep the candidate's handlers for `executeRoll` / `consumeAction` / `loadInitiative` / `startCombat` / `placeTokenOnMap` / `initChannelRef.current?.send` - any hit means it rides a trunk hook (3a tactical / 3b initiative / 3c roll-engine / 3d realtime), not a leaf. The Header (calls startCombat/endCombat + tactical-share + renderHeaderMenu dispatch), the asset sidebar (loadInitiative + addNpcsToCombat + placeFolderOnMap), and the portrait strip (placeTokenOnMap + direct scene_tokens mutation) all FAILED this test despite looking like presentational regions.
- **`useGmTools` is structural prep, not a LOC/UX win - sequence it deliberately.** The hook that absorbs the GM-modal state (`show*` flags + each modal's private sub-state) has an OPEN API-design question: does page destructure the hook so existing call sites are unchanged (safe, but doesn't reduce the modal prop-threading) OR do the modals each take a single `gm` object (reduces threading, but rewires 8 modal interfaces + their mounts = 10+ file touches)? It delivers ~0 LOC reduction and ~0 user value on its own; its only payoff is making the LATER trunk-hook extraction cleaner. So it is NOT a "grab it to keep momentum" unit - it is a deliberate, fresh-context design decision that should be made with intent, not plowed in at the tail of a long window right before a playtest.
- **The state-only cluster move (the chosen `useGmTools` API = page destructures) is the SAFEST extraction variant - and the one precondition is a TDZ check (2026-05-22).** All 9 GM-modal state clusters (restore/reload/loot/cdp/populate/advanceTime/endSession/community/quickAdd) moved with zero behavior risk because the mechanic is purely: lift the `useState` lines into the hook, return them, and add the names to ONE destructure block in page.tsx - every call site (modal mounts, header GM-Tools menu, FeedColumn award-prefill) is untouched, and a missed name fails to RESOLVE under tsc (TS2304), so transcription slips can't survive the gate. ONE precondition: the destructure call site sits lower in the file than the old inline `const`s, so before moving a cluster verify no REAL reference precedes the destructure point (a const used before its declaration is a temporal-dead-zone runtime crash tsc does flag, but cheaper to rule out up front). Method: `grep -n '\bname\b' page.tsx | head -1` per state name; matches that are only the cluster's own comment/definition lines are fine, a real read before the destructure is the blocker. Here every real use was 1000+ lines below the destructure, so it was clean. One-cluster-per-commit kept each step trivially revertable; the page only shed ~11 lines net (breadcrumb comments replace the decls) - the win is structural, not LOC.

## A "fix-do-NOT-preserve" bug fix ships STANDALONE and FIRST, never bundled into the behavior-preserving refactor
- **Context (2026-05-22, 3a tactical view-state fix).** The grand re-arch is "behavior-preserving by default", and each combat-critical hook (3a-3d) carries a known bug it must FIX-not-preserve. The tempting read of "fix it during the rebuild" is to bundle the fix INTO the big hook extraction. Don't. A behavior CHANGE bundled inside a large behavior-PRESERVING refactor makes the eventual 2-client smoke **impossible to localize**: if something desyncs, you can't tell whether the fix or the refactor caused it. Ship the fix as its own small, attributable commit FIRST; the refactor that follows is then purely behavior-preserving and any smoke regression is unambiguously the refactor.
- **The 3a fix was ~90 lines, not a rebuild.** The GM-pinned-to-tactical bug was a state-COUPLING problem (GM's local `showTacticalMap` entangled with the shared `tacticalShared` on every client). Root-cause fix = decouple via a tiny pure helper (`lib/tactical-view.ts`: `shouldRenderTactical` / `shouldFollowSharedTactical`), gate the realtime view-force on `!gmLike` (using the existing stale-closure-safe `gmLikeRef`), and drop the `tacticalShared` term from the GM's render gate. The pure helper is the L2 seed the re-arch wants AND the unit-test surface (8 tests) - so the fix advances the architecture a little without the risky channel migration. **Lesson: most of these "fix in the rebuild" bugs are small coupling/closure fixes that don't actually need the rebuild - do them now, behind a tested pure helper, and the rebuild inherits clean logic.**
- **Player-path-unchanged-by-construction is the cheap safety argument.** The fix only gated behavior on `!gmLike`; players ARE `!gmLike`, so their code path is byte-identical and the change is provably zero-risk for players, fixing only the GM. That made it single-client verifiable (GM side) and safe to ship without blocking on the 2-client smoke. When you can frame a combat-critical change as "this branch is identical for everyone except the role we're fixing," you've de-risked it enormously.
- **(2026-05-22, 3b nextTurn perf) Optimistic UI is SAFE to add when the optimistic state is field-identical to the reload BY CONSTRUCTION.** `nextTurn` advanced the combat turn via two sequential DB writes + a reload before the UI moved (656ms-3.6s/turn). The instant-flip fix sets local initiative optimistically, but the safety comes from: (1) reusing the SAME patch objects (`activation` from `activateUpdate`, the literal `deactivation`) for BOTH the local `setInitiativeOrder` map AND the DB writes - so they cannot drift; (2) the local source array (`order`) being the exact `select('*').order(roll desc).order(name asc)` that `loadInitiative` sets - so the optimistic array equals the post-write reload field-for-field (no reorder, no flicker); (3) the reload still runs (awaited, under the existing re-entry lock) and is the reconcile - a failed write just self-heals when the reload reads DB truth. The two writes also parallelize because they touch disjoint rows (deactivate `.neq(nextId)`, activate only `nextId`). Lesson: don't reach for a pure-helper + unit test on the optimistic MAP (it's trivial and wouldn't catch the real risk); the real risk is "optimistic == persisted", which you eliminate by sharing the patch objects, and which the 2-client smoke confirms. A unit test there would be hollow ceremony.

## When auditing an endpoint, enumerate its SIDE EFFECTS, not just its obvious cost
- **A "cheap row insert" can hide an expensive unauthenticated email send. Trace every branch before assigning severity** (2026-05-21). The first A5.5 rate-limit pass (2026-05-20) rated `log-visit` LOW: "rows inserted into visitor_logs... can't affect users." It stopped at the INSERT. But the same function emails Xero's alert inbox on `visitNumber === 1`, and that gate is computed from the CLIENT-supplied `ip_hash` + suppressed by the CLIENT-supplied `city`, on a `--no-verify-jwt` endpoint whose URL ships in the public bundle. Omit both body fields -> every unauthenticated request fires an email -> Resend-quota DoS + the real new-visitor alarm buried in noise + forged-geo analytics poisoning. That is HIGH, not LOW.
- Rule for any endpoint/route audit: (1) list every side effect per request, not just the headline DB op - emails, external API calls (Resend, Stripe, OSRM), broadcasts, anything that costs money or is an alerting/observability channel; (2) for each side effect, ask "what input GATES it, and is that input client-controlled?"; (3) a side effect that costs money or is an alarm, gated by client input, on an unauthenticated endpoint, is HIGH regardless of how cheap the visible DB write is.
- Meta-lesson: audit CONCLUSIONS go stale / shallow the same way audit LINE NUMBERS do (cf. the M-5 vehicle-polling reversal in todo.md). A re-read with a sharper question ("what fires per request?") beat the first pass. Don't trust a prior severity rating without re-deriving it.

## Roll-Feed Log Patterns (2026-05-10)

**UNIFIED ROW pattern — one mechanic, one row.** When a single in-game event has both a dice roll AND a downstream effect-broadcast, write **one row** that carries both, not two. Set:
- `character_name` = the actor (NOT 'System')
- `label` = the narrative outcome (e.g. `🎯 Marv Successfully coordinated an attack against Avery Xavier with Frankie, Wilson`)
- `die1` / `die2` / `amod` / `smod` / `cmod` / `total` = the real roll values
- `outcome` = the real roll outcome (`'Success'` / `'Wild Success'` / `'High Insight'`)
- `insight_awarded` = `outcome === 'High Insight'` for PCs

Then suppress the standalone `saveRollToLog` write by adding the label to the `isTrimmedRoll` check in `executeRoll` (`app/stories/[id]/table/page.tsx:5478`). `compactRollSummary` strips the emoji and renders the trim; `▸` expands to the dice breakdown.

Reference implementation: Coordinate-success (commit `<pending>`). Sprint is the older pattern (custom outcome value + bespoke banner); both work, but UNIFIED is preferred when the dice math is interesting and the narrative is short.

**Anti-pattern (do not do):** two rows — one for the dice roll, one for the System effect. The second row has `0+0` dice and reads as a duplicate. Visible bug shipped via the Coordinate flow until 2026-05-10.

**Trim pattern for every new outcome value:**
1. Pick whether the row is Tier A (bespoke banner with its own JSX in `RollsFeed.tsx`) or Tier B (narrative trim via `compactRollSummary`).
2. Tier B: add a branch in `lib/roll-helpers.ts:compactRollSummary` that matches your label / outcome and returns the trimmed sentence. Return `null` falls through to the verbose dice card — only acceptable when the row genuinely has no compact form.
3. Hide the `▸` pip on rows with `die1 = die2 = 0` (auto — handled by `hasRealDice` in `RollEntryCard`). If the row has no real dice, design the narrative to stand on its own.
4. Banned in copy: `(critical)` (use 'Moment of Insight as to why it went so well'), em-dash `—`, en-dash `–`, capital `CDP` (use 'Character Development Points').
5. Wild/HI global tag: ` and has a Moment of Insight as to why it went so well`.
6. LI global tag: ` and has a Moment of Insight as to why it went so badly`.
7. Per-check bespoke overrides (Unarmed HI, Stabilize HI, First Impression HI/LI, Group Check LI) live alongside the general pattern and replace the global tag wholesale.

## CRB / Rules Audit Workflow (2026-05-09)
- **Audit precedence is immutable**: Tapestry canon (`tasks/tapestry-rules-canon.md`) > Quickstart > SRD > CRB. Anything in a lower source that contradicts a higher source must be flagged for rewrite, not preserved. Canon is the live platform code (`lib/xse-schema.ts` + `app/rules/*`).
- **Audit findings get split four ways**: 🔴 CONTRADICTION (direct disagreement, must fix), 🟡 STALE (canon revised since, update to match), 🟢 CRB-UNIQUE (not in canon, no conflict — user decides keep/drop/promote), ⚪ TYPO/GRAMMAR (deferred, batched at end). The four-tag system maps cleanly onto how the user wants to act on each.
- **Chapter-by-chapter pacing beats whole-book passes**: a single CRB-sized PDF (~195 pages) won't fit in one response. Process by user-specified page range, append findings to a running log file (`tasks/froms-tos-crb.md`), summarize per-chapter counts in chat. The user picks the page ranges; don't auto-advance.
- **CRB-unique content gets sorted into 4 tiers, not just kept/dropped**: Tier 1 = strong canon promotion (fills real gap), Tier 2 = setting-supplement (Distemper-specific, not core canon), Tier 3 = optional GM-aid (playtest first), Tier 4 = drop. The four-tier sort is what feeds the roadmap.
- **Two-document export pattern after a long audit**: long-term canon-promotion strategy lives in `tasks/roadmap.md` (new file), concrete next-action items get prepended to `tasks/todo.md` flagged sections. Roadmap and todo answer different questions ("what should canon look like" vs "what's queued") — keep them separate but cross-link.
- **Substitution-pass workflow**: after the audit produces the FROM/TO blocks, the rewrite phase is mechanical — receive a chapter txt (or pdftotext extract), apply only the canon-mismatch substitutions from the audit, leave grammar/spelling alone, write the corrected text to a parallel file. User explicit: "this is NOT about spelling or grammar, just about replacing what's old with what's new." Don't expand scope.

- **Role is now normalized to lowercase**: DB trigger `trg_normalize_role` auto-lowercases `profiles.role` on insert/update. All existing rows backfilled. Always compare against `'thriver'` / `'survivor'` (lowercase). No more `.toLowerCase()` needed — but harmless if left in.
- **Supabase email-confirmation links use `verifyOtp`, not `exchangeCodeForSession`**: confirmation emails carry `?token_hash=<...>&type=signup`, not `?code=<...>`. The latter is for OAuth/PKCE. A `/auth/callback` route built only for `code=` silently fails on every signup-confirmation click. Branch on which params are present and call the right API. Cost: an end-to-end signup test on 2026-05-08C produced "Invalid login credentials" because email never got marked confirmed.
- **Postgres grants `EXECUTE` to `PUBLIC` by default on every new function**: writing `GRANT EXECUTE ON FUNCTION foo() TO authenticated` is a no-op for security purposes — `anon` already had it via PUBLIC. To restrict: `REVOKE EXECUTE ... FROM PUBLIC, anon` first, then GRANT. Surfaced 2026-05-08C when Supabase linter flagged `admin_users_with_login` as anon-callable despite the grant.
- **Trigger functions don't need RPC EXECUTE permissions**: triggers fire from DB events and run as the function owner. Revoking EXECUTE FROM `public, anon, authenticated` on every trigger function in `public` is safe defense-in-depth and clears ~30 linter warnings in one shot. See `sql/security-hardening-2026-05-08.sql` Tier 2.2.
- **FK to `auth.users` defaults to `NO ACTION` if you don't specify ON DELETE**: meaning every `DELETE FROM auth.users` errors with FK violations on un-cascaded child tables. The whole DELETE rolls back atomically — partial deletes don't happen. Fix: audit every FK to `auth.users`, set ON DELETE CASCADE for owned data, ON DELETE SET NULL for community-contributed content (where row should persist with attribution cleared). See `sql/fix-auth-cascades-2026-05-08.sql` for the canonical 5-table fix.
- **`information_schema.constraint_column_usage` can hide cross-schema FKs**: the view sometimes doesn't surface FKs from `public.X` to `auth.users` even when they exist. For reliable FK introspection, query `pg_catalog.pg_constraint` directly (`pg_class`, `pg_namespace` joins). Burned ~10 minutes during the cascade audit.
- **Wix DNS doesn't support MX records on subdomains**: even when MX on root works fine. Resend's verification needs an MX on the sending subdomain (`send.example.com`) and Wix returns "this isn't supported" silently. Plan B: migrate DNS to Cloudflare (free, ~30 min). Cloudflare auto-imports existing Wix records before the swap; site stays up if all subdomains were registered (gotcha: Cloudflare's auto-scan can miss `thetapestry.distemperverse.com` style Vercel subdomains — verify the imported list before changing nameservers at the registrar).
- **RLS blocks everything by default**: When creating new tables, always add RLS policies immediately. Storage buckets need separate policies on `storage.objects` — the bucket existing is not enough.
- **Supabase Storage buckets must be created manually**: They don't auto-create from code. Each bucket needs INSERT/SELECT/DELETE policies on `storage.objects` filtered by `bucket_id`.
- **Column must exist before code references it**: Always provide the ALTER TABLE SQL alongside the commit. Don't assume the user has run previous SQL.
- **Every ALTER TABLE migration must end with `NOTIFY pgrst, 'reload schema';`**: PostgREST caches its schema introspection. If the cache predates the column, the API silently strips that column from write payloads — direct DB queries succeed, client updates "revert" on next read. Cost a debug session on 2026-05-04 (pin sort_order revert). Idempotent and cheap; add it unconditionally to every column-add migration.
- **Always `.select()` after `.update()` and check the error**: Fire-and-forget updates with optimistic local state hide RLS rejections, schema-cache misses, and constraint violations. Pattern: `const { data, error } = await supabase.from(t).update(u).eq('id', id).select().maybeSingle()`. If `error` or `!data`, alert and abort — don't repaint.

- **Null-coalescing chains can create false positives**: `npc.wp_current ?? npc.wp_max ?? 10` evaluates to `0` (and filters as "dead") when both fields are null. Only filter entities as dead when their health field has been explicitly set to 0, not when it's null/uninitialized. Use `npc.wp_current != null && npc.wp_current <= 0` instead.
- **Realtime subscriptions must match the events you need**: Subscribing to `INSERT` only means `DELETE` events are invisible to other clients. If a feature clears data (like session end deleting logs), use `event: '*'` so all clients see the change.

## Conventions

- **Architectural fitness functions = ratchets, not staged-file scans (2026-05-22, grand re-arch Phase 1c).** The existing `check-*.mjs` guardrails scan STAGED files for a banned pattern. Architecture conformance is different: scan the WHOLE repo, compare to a committed baseline (`tasks/_baselines/arch.json`), and fail ONLY on regression (a number moving the wrong way). `scripts/check-arch.mjs` does three: LOC ceilings (god-components shrink only), seam leakage (`.from(` outside `lib/data/**`, `.channel(` outside `lib/realtime/**`), prod console (`console.log|warn` in app/components/lib). Re-baseline DOWN with `--save` after an improvement; `--save` refuses to RAISE a number without `--force`. This turns "migrate 1,324 call sites" from an aspiration into a CI-enforced monotonic decrease. Verify the FAIL path when you build a ratchet (lower a baseline by 1, confirm exit 1) - a ratchet that can't block is theatre.
- **Type a seam LOCALLY to avoid a big-bang global typing migration (2026-05-22, Phase 1b).** `lib/supabase-browser.ts`'s client is NOT parameterised with `<Database>`, so all 1,324 inline `.from()` return `any`. Parameterising it globally would surface tsc errors across 98 files at once - not a "pure addition." Instead `lib/data/db.ts` casts the client to `SupabaseClient<Database>` LOCALLY, so repositories get full typing while the rest of the app is untouched until it migrates. Remove the local cast + parameterise globally only once every consumer is on the seam.
- **Mechanical `.from` migration: only UNIFORM operations are cleanly mechanical (2026-05-22, Phase 3).** A repo migration is a safe behavior-preserving string-replace ONLY when many call sites share ONE query shape: build a named repo fn returning the typed `{data,error}` builder (e.g. `getCampaignNpcs(id)` = `.from('campaign_npcs').select('*').eq('campaign_id',id)`, `insertRollLog(rows)`), then prefix-replace `supabase.from('X').op(` -> `repoFn(` so the trailing args + chain (`.eq`, `.select`, `.order`, Promise.all element) are preserved untouched. This took table-page + repo-wide leakage 1324->1266 with zero behavior change. What does NOT migrate cleanly: (1) VARIED writes - `.update(patch).eq('id',x)` with a different patch per site needs per-site arg-reordering (transcription-risky) OR a thin accessor that doesn't really encapsulate (ratchet-gaming); (2) trunk-table queries (initiative_order/character_states/scene_tokens) - migrating them now then rebuilding into useInitiative/useTacticalSync/useRollResolution is double-handling, so they migrate WITH their hook. Writes use a loose payload param (`rows: any`) during migration - the typed-payload tightening is a separate pass (one roll_log site stuffs a DamageResult into a Json column; strict typing surfaced it - logged, deferred to the rebuild). Don't force every `.from` onto a thin wrapper just to drop the ratchet number; that's churn the hook rebuild redoes.
- **Stale-closure-safe realtime hook: deps `[campaignId]` + handlers in a ref (2026-05-22, Phase 1a).** The recurring "one client stops seeing the other" bug comes from channel effects whose dep array includes state/setters, so the channel tears down + resubscribes on unrelated renders. `useCampaignChannel` fixes it structurally: the effect deps are `[campaignId]` ONLY (subscribe once per campaign), and the subscribed callbacks read the latest handler from a ref that's mirrored every render - so you get current closures over current state WITHOUT resubscribing. Plus every handler is auto-wrapped with the Sentry guard (100% coverage vs the old opt-in). This is the pattern every realtime consumer migrates onto in Phase 3.

- **Terminology: the GM has no PCs (locked 2026-05-22).** A **PC** is a Player Character (player-controlled). An **NPC** is a Non-Player Character (GM-controlled). The GM controls NPCs only. NEVER write "GM's PC" or "GM PC" in docs, UI copy, or comments - it's a category error; the GM-controlled combatant is an NPC. Caveat: "**non-GM PC**" is CORRECT and stays - it means a PC controlled by a non-GM user (a player's character), used in RLS/permission contexts.
- **"new window time?" = handoff prompt**: When the user asks `new window time?`, respond with a concise, self-contained prompt they can paste into a new chat to resume. Shape: `I want to <task>. Load <relevant spec files> first.` Should reference the project-surviving files (tasks/todo.md, tasks/spec-*.md, tasks/rules-extract-*.md, tasks/testplan.md, tasks/lessons.md) so fresh-me has everything needed without re-litigating the last session. Example: `I want to build Phase C Communities — weekly Morale Check, Fed/Clothed resource checks, Activity Blocks. Load tasks/spec-communities.md and tasks/rules-extract-communities.md first.` Don't include stuff only meaningful in the current session (recent commit hashes, "we just shipped X"); stick to things fresh-me can actually reload.

- **Silent Supabase UPDATE failures under RLS are the #1 "feature looks broken but code looks fine" cause**: Supabase `.update()` returns `{ error: {...} }` without throwing. `console.warn('[tag] update error:', error.message)` is easy to lose in the noise.
