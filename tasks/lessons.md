# Lessons Learned

## Don't present a decision menu that includes corner-cutting options - when the root-cause fix is clear, state it as THE answer and plan it (2026-05-26)

For the tactical-map img_scale divergence I gave Xero an A/B/C menu: A = keep the art + fix the render properly, B = drop backgrounds entirely, C = ship a center-on-token band-aid only. Xero: "stop cutting corners ... isn't A the right answer?" It was - A was always the answer. The mistake: B *degrades the product* (drops his map art) and C is *symptom-only*, yet I lined them up beside the real fix as if they were peers, making Xero do the work of rejecting the lesser paths. This is the same class as the banned quick/full menu (memory `feedback_never_offer_quick`), just subtler - the lesser options weren't labelled "quick," they were "drop a feature" and "band-aid." Rule: when the correct root-cause fix is identifiable, present it as the plan, not as one choice among ways to do less. A genuine safety-net (the center-on-token button) is fine to ship *alongside* the real fix while it's built, but never framed as an *alternative to* it. Risk/timing is handled by PHASING the real fix (plan it, do it with margin + an eyeball if it's load-bearing), not by offering a smaller fix. See `feedback_never_offer_quick` (recurrence logged there too).

## "Only 2 of 4 placed tokens show" = an UNGUARDED async reload race dropping data; when the DB is correct but the screen isn't, suspect a stale-fetch-overwrite, and guard EVERY setState-from-async-fetch with a sequence counter (2026-05-25)

The final chapter of the map-token saga, and the one I should have found first. After clear `+/✓` Map labels shipped, Xero added all 4 PCs and still saw "only 2 on the map." I'd been re-placing/clustering/un-archiving (data patches) for several rounds. The break came from comparing the DB to the screen: a live query showed all 4 PCs LIVE, visible, non-overlapping at (1,1)(3,1)(5,1)(7,1) - the data was flawless - yet the client rendered 2. That divergence (DB right, client wrong) means the CLIENT dropped them, not a placement/viewport/occlusion problem. Root cause: `loadTokens` did `setTokens(await fetch)` with NO sequence guard. Rapid placement fires several overlapping reloads (each `+ Map` bumps `tokenRefreshKey` AND the `scene_tokens` realtime sub fires); the fetches resolve out of order, and a slower EARLIER fetch (taken when only 2 tokens existed) lands last and overwrites the full set with its stale snapshot. Intermittent by nature (pure timing), which is why it dodged every theory. `loadEntries` already had this exact guard (a `++seqRef.current` checked after the await); `loadTokens` didn't. Fix: same pattern - `const seq = ++loadTokensSeqRef.current; ...await...; if (seq !== loadTokensSeqRef.current) return; setTokens(...)`. Lessons: (1) **When the DB row is correct but the UI shows something else, it's a CLIENT bug - stop patching the data.** Query-vs-render divergence is the fastest triage; I burned ~6 rounds of DB band-aids before doing it. (2) **Any `setState(await fetch())` that can be triggered concurrently (realtime sub + a manual refresh key + rapid user actions all calling the same loader) MUST have a sequence guard**, or a stale resolve silently clobbers fresh state. Audit sibling loaders for the same shape - loadEntries had it, loadTokens didn't; check loadScenes/loadInitiative/etc. (3) The playtest-recorder clickstream confirmed the trigger (4 rapid `+ Map` clicks) - read it earlier next time. (4) Don't hand the user a "don't click so fast / don't touch the button" workaround for a race; fix the race (see [[feedback_no_workaround_instead_of_fix]]).

## "Tokens won't appear" was the VIEWPORT centering on the map middle while tokens spawn top-left - and I shipped a wrong fix from a handoff hypothesis FIRST because I didn't verify DB+render before coding (2026-05-25)

The catastrophic P1 close of the map-token saga, and a process failure worth not repeating. A handoff said tokens were hidden behind the day/fog TOOLBAR (occlusion); I trusted that hypothesis and shipped a toolbar-centering fix WITHOUT first verifying. Xero came back: still broken. Only THEN did I do what I should have done first - (1) queried the live DB (`npx supabase db query --linked -f`): the 3 PCs were present on the active scene, non-archived, is_visible=true; (2) read the GM render path: it draws EVERY token unconditionally (`if (isGM) return true` in the visibility filter; `if (!t.is_visible && !isGM) return` in the draw loop). Rows correct + render unconditional => the bug is NOT data and NOT the draw; it can only be the VIEWPORT. Found it: `centerViewport()` scrolled the container to the geometric MIDDLE of the (large) canvas on scene open, but tokens spawn at the LOCKED top-left (1,1) = canvas px ~(37,37), which is scrolled off the top-left edge of a middle-centered view. The tell was right there in the data the whole time: Shimmy was visible earlier at center grid (32,22) but invisible at (5,1) - the cluster had moved into the corner the view never shows. Fix: frame scene-open on the token centroid, and smooth-scroll a token that APPEARS mid-session (player-bar Map button / un-archive) into view; pure centroid+clamp math in lib/tactical-view.ts (tested), DOM appliers there too so the LOC-ratcheted TacticalMap stays at baseline. Lessons: (1) **a single symptom can have THREE independent causes across a saga (stacking spawn -> toolbar occlusion -> viewport offset); "I fixed it" after one is a hypothesis until the user confirms.** (2) **Before coding ANY fix off a handoff/bug-report hypothesis, spend 5 minutes proving the layer: read the DB for "do the rows exist + are they correct", read the render for "would it draw", THEN you know which layer to fix.** I had the tools to find the real cause in the first pass and skipped them because the handoff sounded authoritative - that cost a wrong ship and a P1 round-trip. This is exactly feedback_locate_before_diagnose + feedback_accuracy_over_confidence; the handoff is a hypothesis, not a finding. (3) When a canvas can dwarf the viewport, "the row exists and would draw" still isn't "the user can see it" - viewport scroll position is a third visibility gate after data and occlusion.

## When a locked game-geometry value collides with movable UI chrome, move the CHROME - and when adding to a god-component trips check-arch, extract the logic into a lib hook (the ratchet WANTS that) (2026-05-25)

Third + final chapter of the "tokens won't appear on the map" saga. The first two fixes chased token SPAWN (occupancy spiral, then constrain the spiral to stay clear of the top-left corner). The real remaining bug: even the locked `(1,1)` anchor sits UNDER the draggable day/fog toolbar (default `{8,8}`, `zIndex:10`), so top-left tokens render behind it. Two reusable points. (1) **When a LOCKED value (here the `(1,1)` spawn, locked by Xero 2026-05-22 + guarded by a unit test + a memory) collides with a piece of movable UI chrome, move the CHROME, not the locked thing.** The toolbar is draggable, position-persisted, GM-only furniture - nothing depends on its default; the spawn is load-bearing game geometry with a lock. So the fix centers the toolbar's DEFAULT (computed from the live canvas+bar width on mount via a callback ref, not a hardcoded pixel - a fixed "center" only looks centered on one screen width, and this exact spawn-vs-chrome target had already been moved 4 times) and leaves spawn untouched. Migration nuance: a saved `{8,8}` is the OLD corner default, indistinguishable from "never moved," so treat it as un-chosen and re-center; only a genuine NON-corner drag is a deliberate choice to keep. (2) **`scripts/check-arch.mjs` (a pre-commit ratchet) blocks ANY net LOC growth in the god-components it tracks - and COMMENTS count.** My first cut added ~68 lines to `TacticalMap.tsx` (mostly rationale comments) and the hook blocked the commit. Do NOT `--no-verify` past it (bright line). The ratchet's stated intent is "god-components only shrink; move logic to lib/**" - so the elegant fix that ALSO unblocks the commit is to extract the feature into a lib module: I moved all the fog-bar position state/persistence/centering/reset into `lib/use-fog-bar-position.ts` and aliased its return in the destructure (`pos: fogBarPos`, etc.) so the component body barely changed. Net: the component SHRANK below baseline, the ratchet went green (even reported the file as improved), and the centering geometry became a pure `centeredToolbarX()` helper with unit tests (the component itself can't be layout-tested - jsdom `getBoundingClientRect` returns 0). Rule for the Hunt & Peck lane: when check-arch blocks you for LOC growth in a tracked component, don't shave comments to squeak under the grace - lift the new logic into `lib/` (hook or pure fn). It satisfies the ratchet by design and is the better structure anyway.

## Wiring a client to a both-sides atomic RPC: DROP the client's own-side write (double-spend vs the RPC's row lock) and refresh the SENDER explicitly (broadcasts don't echo to their sender) (2026-05-25)

Landing the PC-trade fix - rewiring `onGiveItem` from a raw cross-user `.update` (the silent-no-op data-loss) to the `give_item_to_character` SECURITY DEFINER RPC. Three reusable points. (1) **When an RPC moves BOTH sides of a transfer atomically, the client must stop doing ANY of its own inventory writes** - the old flow had `InventoryPanel.confirmGive` decrement the GIVER (own-row, RLS-allowed) AND `onGiveItem` write the RECEIVER. Keeping the giver decrement alongside the RPC double-spends: the RPC does `SELECT ... FOR UPDATE` on the giver then `have - qty`, and a racing client `.update` that committed first makes the RPC read the already-decremented value and subtract AGAIN. So I guarded the client giver-decrement with `if (target.kind !== 'pc')` - other give kinds (NPC/community/vehicle) write GM-owned campaign tables, not the giver's row, so they keep their decrement. (2) **A Supabase broadcast does NOT echo to its sender**, so the existing `inventory_transfer` -> `loadEntries` refresh only updated the RECEIVER's client; the giver (who initiated) needed an explicit `loadEntries(id)` after the RPC to re-sync its own open modal. Easy to miss because the receiver "just works" via the broadcast. (3) **Verify the RPC actually exists on prod before wiring the client to it** - the SQL file's header said "NOT YET APPLIED" but PF's lane note + a commit said it was live; a `pg_proc` check via the linked main checkout settled it (it was applied; the file header was stale). Don't trust a stale file comment over the live catalog. The regression net: un-fixme the `inventory-trade.spec` PC-trade test (marv->percy: item MOVES, receiver gains + giver loses, reversible capture/restore via each owner's own session) - it tests the RPC + RLS (the data-integrity core); the thin client RPC-call is covered by tsc + the full re-cert.

## A "free" grid cell is not necessarily a VISIBLE one - auto-placement must exclude UI-occluded cells (2026-05-25)

The token spawn-spread fix (spiral out from the (1,1) anchor to the nearest free cell) shipped clean + unit-tested, but a follow-up playtest showed a 2nd/3rd PC landing on (0,0) / the top row - invisible, because the draggable day/fog toolbar sits in the top-left corner of the tactical canvas. The original `(1,1)` anchor existed PRECISELY to clear that toolbar (per the lib history comment), and my spiral happily stepped back into the corner it was avoiding. Fix: constrain the spiral to x>=anchorX, y>=anchorY (down-right only). Lesson: when auto-placing things on a canvas, "unoccupied by other tokens" is not the same as "visible to the user" - the occupancy check must also exclude cells hidden behind fixed/floating UI (toolbars, panels, the corner furniture). When you add a free-cell search near an anchor that was chosen for a reason, preserve that reason (here: stay clear of the corner), don't just treat all in-bounds free cells as equal. Also: a unit test that asserts "distinct, non-stacking" cells passed while the real bug (hidden cells) slipped through - the regression test now also asserts x>=1 && y>=1.

## A text input bound to realtime-synced state + write-per-keystroke fights the typist - edit a local draft, commit on blur (2026-05-25)

Report: the SCENE NAME field was "very hard to type in" - "Storage" came out "Strorg e". Cause: the input was `value={scene.name}` with `onChange` writing `scene.name` to the DB on EVERY keystroke, and the popout subscribed to `tactical_scenes` `postgres_changes` -> `load()` -> `setScene`. So each keystroke fired a write, the realtime echo round-tripped back a few ms later with the LAGGING committed value, and `setScene` reset the controlled input mid-typing - cursor jumps to end, characters land out of order. The classic "controlled input fighting an async source." Fix: the input edits a LOCAL draft (`nameDraft` useState), commits once on blur / Enter, and the draft re-seeds from the synced value ONLY when the entity id changes (a `useEffect(... ,[scene?.id])`) - so realtime echoes for the same entity never clobber in-flight typing. Reusable rule: never bind a free-text `<input>`/`<textarea>` directly to state that a realtime subscription overwrites, AND never write-per-keystroke to a row you're also subscribed to. Use a local draft + debounce-or-blur commit, and gate the "re-sync from server" on an id change, not every refresh. Footgun class: audit other live-bound text fields (GM/vehicle/character notes, campaign fields) for the same shape.

## Before building a spec against an optional-migration table, verify it exists on PROD (via the linked MAIN checkout, not the worktree); scope test social content to Global; find a row among prod volume via a stable id + search (2026-05-24)

Building `campfire-lfg-warstory.spec`. Four reusable points. (1) **Some tables are optional migrations that may not be applied on prod** - the war-stories page literally renders a "War Stories isn't live on this database yet - a Thriver needs to apply sql/war-stories.sql" banner and DISABLES its composer when `war_stories` is absent. Don't assume a table exists because the UI references it; verify first. (2) **The supabase CLI is linked in the MAIN checkout (`C:\TheTapestry`), NOT the per-lane worktree** - `npx supabase db query --linked -f <file>` from the worktree fails "Cannot find project ref"; run it from `C:\TheTapestry`. Confirmed lfg_posts/lfg_interests/war_stories/war_story_reactions all live before writing a line. (3) **Turn a UI fallback into a positive precondition assertion:** the war-stories "+ New Story" button is `disabled={tableMissing}`, so asserting `toBeEnabled()` IS the live-schema gate - cheaper + clearer than a separate existence probe in the test. (4) **Composers that default their scope to a real campaign will attach test content to it** - the war-story composer auto-picks the GM's most recent real campaign (`myCampaigns[0]`); click the Global scope button so the `[E2E]` post lands nowhere real (campaign_id null), and assert `{status:'approved', campaign_id:null}` to prove BOTH the auto-approve AND the scope. (5) **To find a freshly-created row among prod's real volume (the list paginates), don't rely on it being on the first page** - use the page's own search box to filter to the unique `[E2E]` title, then scope the action click to the row's stable DOM id (`#lfg-<postId>`, lfg/page.tsx:749) rather than a CSS-styled name. Same "gate on a stable control/id, not the styled text" rule as the npc-roster folders.

## "X won't appear on the map" had TWO causes, neither a render bug - query the live DB for the actual rows before assuming the UI is broken (2026-05-25)

Playtest report: GM "couldn't get character tokens to appear on the map." The instinct is a render/realtime bug. A live-DB read (`npx supabase db query --linked -f`) of `tactical_scenes` + `scene_tokens` for the campaign showed the tokens WERE inserted - the symptom had two unrelated causes: (1) every token spawned on the same cell (1,1) (`defaultSpawnCell` always returned (1,1), no occupancy check), so 3 placed PCs stacked into one; and (2) the ACTIVE scene was a blank "New Map" (4 dupes created in ~1s by a mashed "+ New Map" button, each `createScene` activating+deactivating), while the GM's real battle maps - which already had every PC placed - sat inactive. So the tokens landed on a blank map the GM wasn't expecting, stacked. Lessons: (1) when a user says "it didn't appear/save/work," READ THE DB FIRST - "the row exists but isn't visible" vs "the write never happened" are opposite fixes, and the clickstream/telemetry (repeated clicks on the same button) confirms "nothing visibly happened" without telling you why. (2) A single symptom can have multiple independent causes; don't stop at the first. (3) Watch for `.single()` on `is_active=true`: it hard-errors on multiple-active (the racy create can produce that), turning a data state into a misleading "no active scene" alert. (4) An "active/current" singleton (one active scene, one active combatant) that's set by separate insert-then-deactivate steps will accumulate duplicates under rapid/concurrent fire - guard the creator with an in-flight ref.

## Extending a CERTIFIED spec: add a separate test (don't bolt onto the green one), assert version/update flows semver-AGNOSTICALLY, and verify a UI affordance's query is SCOPED before asserting it on the shared live account (2026-05-24)

Adding Ch14.4 (module v2 "update available" notice) as a 2nd test in `rumors-publish-clone.spec`. Three reusable points. (1) **When a new flow depends on an already-certified flow as its precondition (here: publish v1 + clone), give it its OWN test with its OWN full setup + teardown rather than appending steps to the certified test.** A flake in the new, less-proven steps would otherwise redden the certified coverage too - separate tests keep independent signal. The cost (re-running the shared setup) is worth it; same-file tests run serially under `fullyParallel:false` so there's no cross-contamination, and distinct `[E2E]` names disambiguate the two campaigns. (2) **Assert update/version flows WITHOUT hardcoding the resulting version string.** The publish-v2 path defaults to a `minor` bump (1.0.0 -> 1.1.0 via `bumpSemver`), but that default could change; so assert `module_versions` COUNT >= 2 + the StoryActionBar update notice's VERSION-INDEPENDENT title (`getByTitle(/has a newer version/i)`, StoryActionBar.tsx:284) instead of `getByText('v1.1.0')`. The notice only renders when `latest_version_id != subscription.current_version_id`, so its mere presence proves the bump propagated. (3) **Before asserting a "global-ish" UI affordance (notification, badge, update chip) on a LIVE shared test account, read the query that drives it and confirm it's scoped to your fixture.** The update check is `.eq('campaign_id', campaignId)` (StoryActionBar.tsx:113) - scoped to the campaign whose hub you're on - so the gm account's OTHER real outdated subscriptions can't make the notice appear on the clone hub falsely. Had it surfaced "the first outdated subscription account-wide," the assertion would have been a false-positive landmine on prod. Verify the scope; don't assume.

## Seed a JSONB-array sub-entity by PATCHing the PARENT row as its owner - the in-app RPC indirection is only for NON-owner writers, not for you (2026-05-24)

Building `vehicle-maintenance-checks.spec` (Install Fuel Drum + Gather Materials checks on the vehicle popout). Four reusable points. (1) **A vehicle is not its own table - it lives inside `campaigns.vehicles` (a JSONB array).** To seed one you don't INSERT a row, you PATCH the parent campaign: `PATCH /rest/v1/campaigns?id=eq.<id>` with `{ vehicles: [V] }`, and you hand-build `V` from the `Vehicle` TS interface (every required field: id/name/type/rarity/size/speed/passengers/encumbrance/range/wp/fuel/stress/cargo/three_words/notes/image_url + the optional feature fields you're exercising). (2) **The in-app writer routes through an `update_vehicle_in_campaign` SECURITY DEFINER RPC, but that's ONLY because the popout must let non-GM campaign MEMBERS write** (the "GM can update campaigns" RLS policy rejects non-GM direct writes, so members need the RPC). A test acting as the campaign-OWNING GM can PATCH the JSONB column DIRECTLY - the RPC indirection in the app code is a red herring for seeding. Lesson: when app code wraps a write in an RPC, check WHY before assuming you need it; if it's an RLS workaround for a less-privileged caller, the privileged caller (owner/Thriver) can often write direct. (3) **A minimal `campaign_npcs` row (`{campaign_id, name}` only) is enough to satisfy a "crew.length > 0" gate** - `openCheck('install'|'gather')` alerts "Add a crew member" and never opens the modal if the crew pool is empty. The popout's crew filter keeps an NPC even with null `wp_current` (the dead-check is `wp===0 && death_countdown != null`, and a bare insert leaves death_countdown null). So one no-stats NPC unblocks the flow without seeding a PC (which needs campaign_members + characters). (4) **For a RollModal-driven dice action, the post-roll "Close" button REPLACING the "Roll" button is the unambiguous "it resolved" signal** (pre-roll has Cancel+Roll; post-roll has Close) - gate on Close becoming visible, then take the authoritative dice-independent proof from the DB: the `roll_log` row tagged `damage_json->>checkKind=eq.<kind>` with `outcome` in the six valid XSE outcomes. Don't parse the on-screen outcome banner for the VALUE (dice-driven), and beware the effect-message badge also contains outcome words ("Failure - the drum is damaged..."), so a `getByText(/Failure|.../)` matches two nodes - use `.first()` for "some outcome rendered" and the roll_log row for the real assertion. ONE test seeded once ran BOTH checks against one vehicle (independent fields: install touches fuel_max/cargo, gather touches brewing_supplies), halving the slow `/stories/new` step; full re-cert stayed green (122 passed + 2 known watch-list flakes absorbed by retries).

## Per-lane worktree: after pushing an apply-able SQL (or any file Xero runs/opens), FF-sync the main checkout (2026-05-24)

Puffer Fish works in `C:\TheTapestry-puffer` (branch `lane/puffer`) and pushes to `main`. But Xero runs operator commands (`npx supabase db query --linked -f sql/<file>.sql`) and looks for files from the MAIN checkout `C:\TheTapestry`. That checkout does NOT auto-update on a push - it sat 3 commits behind, so `give-item-to-character-rpc-2026-05-24.sql` (committed + on origin/main) appeared to "not exist" when Xero went to apply it. Fix was a one-liner: `git -C /c/TheTapestry fetch origin && git -C /c/TheTapestry merge --ff-only origin/main` (safe - only untracked WIP there, no tracked changes, so it fast-forwards clean).

**Rule:** this is the existing memory `feedback_working_directory` ("after every push from a worktree, pull into main checkout") - the 3-lane split makes it sharper: the moment you push a SQL file (or anything) Xero needs to run/open, FF-sync `C:\TheTapestry` in the same step. Doc-only commits can lag harmlessly; apply-able artifacts cannot. Don't make Xero hunt for a file that's "committed but not on his disk." (FF-only, never force; if it won't fast-forward, that's a real divergence to look at, not to paper over.)

## A literal `*/` inside a `{/* JSX comment */}` closes the comment early and breaks the parse - watch for it in prose like "Mechanic*/Tinkerer" (2026-05-24)

Adding the install/gather roller picker, tsc failed with `TS1005 '}' expected` + `TS1381 Unexpected token` on a line that looked fine. Cause: a JSX block comment `{/* ... via switchRoller (install re-picks Mechanic*/Tinkerer; gather reads Scavenging). */}` - the `*/` in "Mechanic*/Tinkerer" terminated the comment mid-sentence, so the trailing "Tinkerer; ...). */}" became stray JSX and the parser choked several tokens later (the reported line/col was downstream of the real cause, as usual for brace errors). Fix: don't put a bare `*/` (or `/*`) inside a JSX comment - reword ("Mechanic or Tinkerer") or space it ("Mechanic\* / Tinkerer"). This bites specifically with the codebase's `Mechanic*` skill notation, which pairs a `*` with any following `/`. When a JSX edit throws a TS1005/TS1381 brace error, scan the nearest `{/* */}` comment for an inner `*/` before hunting the braces it points at.

## Extracting a slice of a LOC-ratcheted god-component: move it to a hook returning { handler, modal }, transcribe VERBATIM, prove identical with tsc + the existing unit suite (2026-05-24)

The vehicle popout (`app/vehicle/page.tsx`) hit its arch-ratchet ceiling (2088 / 2101 hard fail, 13 lines headroom) so the next feature (install/gather skill-checks) physically could not go inline. (5) Phase the risk: ship the pure extraction ALONE (own commit, bisectable/revertable) and gate the feature-add behind a HUMAN smoke of the load-bearing path (here a 2-client mounted-weapon attack = damage + initiative-decrement), because the extraction touching the combat roll path is exactly where a silent behaviour change would hurt most.

## When a UI action writes TWO rows in sequence, poll for the SECOND - a one-shot query races the slower insert under full-suite load (2026-05-24)

`rumors-publish-clone` passed standalone but FAILED all retries in the full-suite re-cert (120 passed, 1 failed) - the re-cert earning its keep again. Cause: publish writes the `modules` row THEN the `module_versions` row (`publishModuleVersion`, lib/modules.ts:752 then :796). My test polled for the modules row (appears first -> passes) and then did a ONE-SHOT query for the version - which under full-run load hadn't committed yet, so it got `[]` and failed `toContain('1.0.0')`. ## Multi-lane push escape: cherry-pick into a detached worktree, then `reset --mixed` (2026-05-24, validated)

When the main checkout is too cluttered with the OTHER lane's untracked files to `git pull --rebase` (rebase does a checkout and dies on "untracked working tree files would be overwritten" - e.g. a leftover untracked `e2e/*.spec.ts` the other lane has since committed), do NOT delete their files or `--no-verify`. The reliable escape (used successfully this session to land Phase 2):
1. `git worktree add --detach .claude/worktrees/pushwt origin/main` (clean tree, no untracked junk -> ratchet green, no collision).
2. In it: `git cherry-pick <your-local-sha>` then `git push origin HEAD:main`. (Cherry-pick is clean when your diff doesn't overlap the other lane's commit.)
3. Back in the main checkout: `git fetch origin main` then `git reset --mixed origin/main` - moves the branch pointer to the new main WITHOUT touching the working tree, so the other lane's uncommitted work is preserved and your now-pushed files show as clean.
4. Clean up: you must `cd` OUT of the worktree first (Windows holds a lock on the cwd -> "Permission denied"); then `git worktree remove ... --force`, `git worktree prune`, and `rm -rf` the dir if it lingers.

Two gotchas hit this session: (a) the Bash tool's cwd PERSISTS across calls, so after `cd`-ing into the worktree, later relative paths resolve from there - use `git -C <abs-path>` instead of relative `cd`. (b) `git worktree remove` fails with Permission denied while your shell sits inside that worktree.

## God-component function extraction: byte-exact script move + destructure-deps + tsc convergence (2026-05-23)

**Technique** for lifting a huge function (here: the ~1810-line `executeRoll`) out of a god-component into a hook/module WITHOUT risking a silent behavior change. Reused for every Phase 5 god-component extraction.

1. **Find exact boundaries** (`grep -n` the function + its neighbor). Confirm the closing brace line.
2. **Slice the body with a script** (node `readFileSync().split(eol).slice(start,end)`), do NOT retype it. Retyping 1800 lines from context WILL drift. **Detect CRLF vs LF** and split/join on the actual EOL - Windows files are `\r\n`, and `split('\n')` leaves a `\r` on every line that breaks all string matching.
3. **Move the body VERBATIM** into `useX(deps) { const {...} = deps; <BODY>; return { fn } }`. Destructure every dependency at the top so the body text is unchanged (no `deps.` prefixing - that's 40+ error-prone edits). The page destructures the fn back out; call sites stay unchanged. Same pattern as `useGmTools`.
4. **Derive the deps set mechanically, not by eye:** tokenize the body, intersect with the component's declared identifiers (useState/useRef/function/const at 2-space indent) = deps; intersect with the import block = needed imports. BUT the tokenizer also catches comment mentions and string-literal keys (e.g. `groupCheckParticipants:` as an object key, or a name in a `//` comment) - so **grep the body for each candidate's real CODE usage** before trusting it. Over-inclusion is safe (unused destructure, no `noUnusedLocals`); under-inclusion is caught by tsc.
5. **tsc is the completeness oracle, both directions:** a missing dep -> "Cannot find name X" inside the hook; a spurious dep -> "Cannot find name X" at the call-site object. Iterate to clean. Watch for TDZ: any dep declared AFTER the extracted function must be hoisted to the call site (here: `syncedSelectedEntry`) - it was a hoisted `function` before (always available) but a hook CALL runs in place.
6. **PROVE behavior preservation:** diff the extracted body against the git-HEAD original (`git show HEAD:file | slice`) after CRLF-normalizing - assert byte-identical. Then assert the hook file `.includes()` that body verbatim. Only then is "behavior-preserving" a fact, not a hope.
7. **Type the deps interface from source:** copy inline state types verbatim (e.g. the `mapTokens` shape), refs as `MutableRefObject<T>`, setters as `Dispatch<SetStateAction<T>>`, `supabase` as `ReturnType<typeof createClient>`. If a function's real return type bites (saveRollToLog returns `{total,outcome,insightAwarded}` not void) and the body ignores it, type the return precisely or `any`-the-ignored-field. Note the dual `RollResult` (./types interface vs lib/roll-outcomes union) - disambiguate.
8. **Do NOT also refactor** (pure/effect split, dedup, rename) in the same commit. Relocation-only keeps a 2-client / smoke failure localizable to "the move," not "the move plus 5 changes."

## Deleting a local var that shares a name with component state = silent rebind, not a compile error you'd expect (2026-05-23)

**Rule:** Before deleting a `let`/`const` local, grep the enclosing function for an outer-scope binding of the SAME name. If one exists, every reference to the local silently rebinds to the outer one instead of erroring "undefined."

**What it caught (3c-B1):** `executeRoll` had local `let distractResult = ''` / `let stabilizeResult = ''` (dead branches being removed), but the component ALSO has state vars `distractResult` / `stabilizeResult` (type `SharedRollResult | null`, for the dedicated modals). The `traitNotes` array spread `...(stabilizeResult ? [stabilizeResult] : [])` read the locals. Deleting just the branches (not the spreads) would have left the spreads compiling fine - but now reading the COMPONENT STATE objects and pushing `SharedRollResult` into a `string[]`. tsc would have flagged the array-type mismatch here, but a same-typed shadow (string local shadowing a string state) would NOT - it'd silently change runtime behavior with a green build. The phase4-prestage commit knew this and removed the spreads too; I verified and matched.

**Detection:** when removing a local, search the whole component for the identifier. Adjacent surviving references to a now-removed local are a rebind risk, not a guaranteed compile failure. This is why behavior-preserving deletions need the grep, not just "tsc passed."

## The arch ratchet (`scripts/check-arch.mjs --save`) is one-way - it never re-baselines a god-component UPWARD (2026-05-23)

## Reading image-only PDF tables: PyMuPDF render -> PNG -> vision (2026-05-20)

**Technique.** The Quickstart + CRB rulebook tables are images with no text layer (`pdftotext` / Grep on the `.txt` returns nothing; `page.search_for()` returns empty). The PDF Read tool also fails (`pdftoppm` not on PATH). Working path:

```python

import fitz
doc = fitz.open(r'docs/Rules/<file>.pdf')
pg = doc[PAGE_INDEX]              # 0-indexed
clip = fitz.Rect(x0, y0, x1, y1) # crop to the table region (fractions of page rect)

pix.save(r'.claude/tmp-x/out.png')
```

Then Read the PNG (vision). Iterate the clip rect + zoom until the table is crisp. Clean up the temp PNGs after (`rm -rf .claude/tmp-x`). On Windows use the `py` launcher, not `python` (the bare alias routes to the Microsoft Store stub). This is how the explosives audit (Table 13) got read.

## Never combine `git stash push <file>` with rebase --autostash (2026-05-19)

**Banned workflow.** Cost ~30 min today + a silent missing-fixes ship (`d5fd410`).

```sh

git stash push supabase/.temp/cli-latest         # stash one specific file
git fetch + git -c rebase.autoStash=true rebase  # autostash kicks in
git commit -m "..."                              # commits stale state
```

What happened: the autostash flag tried to stash any UNSTAGED working-tree changes for the rebase. My specific-file stash plus the autostash dance silently UNSTAGED my 13 `git add` targets. **Correct workflows:**

1. **One-shot ignore:** add the offending file to `.gitignore` first, untrack it (`git rm --cached`), then proceed without stashing.

## A "fix-do-NOT-preserve" bug fix ships STANDALONE and FIRST, never bundled into the behavior-preserving refactor
- **Context (2026-05-22, 3a tactical view-state fix).** The grand re-arch is "behavior-preserving by default", and each combat-critical hook (3a-3d) carries a known bug it must FIX-not-preserve. The tempting read of "fix it during the rebuild" is to bundle the fix INTO the big hook extraction. Don't. A behavior CHANGE bundled inside a large behavior-PRESERVING refactor makes the eventual 2-client smoke **impossible to localize**: if something desyncs, you can't tell whether the fix or the refactor caused it. Ship the fix as its own small, attributable commit FIRST; the refactor that follows is then purely behavior-preserving and any smoke regression is unambiguously the refactor.
- **The 3a fix was ~90 lines, not a rebuild.** The GM-pinned-to-tactical bug was a state-COUPLING problem (GM's local `showTacticalMap` entangled with the shared `tacticalShared` on every client). Root-cause fix = decouple via a tiny pure helper (`lib/tactical-view.ts`: `shouldRenderTactical` / `shouldFollowSharedTactical`), gate the realtime view-force on `!gmLike` (using the existing stale-closure-safe `gmLikeRef`), and drop the `tacticalShared` term from the GM's render gate. The pure helper is the L2 seed the re-arch wants AND the unit-test surface (8 tests) - so the fix advances the architecture a little without the risky channel migration. **Lesson: most of these "fix in the rebuild" bugs are small coupling/closure fixes that don't actually need the rebuild - do them now, behind a tested pure helper, and the rebuild inherits clean logic.**
- **Player-path-unchanged-by-construction is the cheap safety argument.** The fix only gated behavior on `!gmLike`; players ARE `!gmLike`, so their code path is byte-identical and the change is provably zero-risk for players, fixing only the GM. That made it single-client verifiable (GM side) and safe to ship without blocking on the 2-client smoke. When you can frame a combat-critical change as "this branch is identical for everyone except the role we're fixing," you've de-risked it enormously.
- **(2026-05-22, 3b nextTurn perf) Optimistic UI is SAFE to add when the optimistic state is field-identical to the reload BY CONSTRUCTION.** `nextTurn` advanced the combat turn via two sequential DB writes + a reload before the UI moved (656ms-3.6s/turn). The instant-flip fix sets local initiative optimistically, but the safety comes from: (1) reusing the SAME patch objects (`activation` from `activateUpdate`, the literal `deactivation`) for BOTH the local `setInitiativeOrder` map AND the DB writes - so they cannot drift; (2) the local source array (`order`) being the exact `select('*').order(roll desc).order(name asc)` that `loadInitiative` sets - so the optimistic array equals the post-write reload field-for-field (no reorder, no flicker); (3) the reload still runs (awaited, under the existing re-entry lock) and is the reconcile - a failed write just self-heals when the reload reads DB truth. The two writes also parallelize because they touch disjoint rows (deactivate `.neq(nextId)`, activate only `nextId`). Lesson: don't reach for a pure-helper + unit test on the optimistic MAP (it's trivial and wouldn't catch the real risk); the real risk is "optimistic == persisted", which you eliminate by sharing the patch objects, and which the 2-client smoke confirms. A unit test there would be hollow ceremony.

## When auditing an endpoint, enumerate its SIDE EFFECTS, not just its obvious cost
- **A "cheap row insert" can hide an expensive unauthenticated email send. Trace every branch before assigning severity** (2026-05-21). The first A5.5 rate-limit pass (2026-05-20) rated `log-visit` LOW: "rows inserted into visitor_logs... can't affect users." It stopped at the INSERT. But the same function emails Xero's alert inbox on `visitNumber === 1`, and that gate is computed from the CLIENT-supplied `ip_hash` + suppressed by the CLIENT-supplied `city`, on a `--no-verify-jwt` endpoint whose URL ships in the public bundle. Omit both body fields -> every unauthenticated request fires an email -> Resend-quota DoS + the real new-visitor alarm buried in noise + forged-geo analytics poisoning. That is HIGH, not LOW.
- Rule for any endpoint/route audit: (1) list every side effect per request, not just the headline DB op - emails, external API calls (Resend, Stripe, OSRM), broadcasts, anything that costs money or is an alerting/observability channel; (2) for each side effect, ask "what input GATES it, and is that input client-controlled?"; (3) a side effect that costs money or is an alarm, gated by client input, on an unauthenticated endpoint, is HIGH regardless of how cheap the visible DB write is.
- Meta-lesson: audit CONCLUSIONS go stale / shallow the same way audit LINE NUMBERS do (cf. the M-5 vehicle-polling reversal in todo.md). A re-read with a sharper question ("what fires per request?") beat the first pass. Don't trust a prior severity rating without re-deriving it.

## Roll-Feed Log Patterns (2026-05-10)

**UNIFIED ROW pattern — one mechanic, one row.** When a single in-game event has both a dice roll AND a downstream effect-broadcast, write **one row** that carries both, not two. Set:
- `character_name` = the actor (NOT 'System')
- `label` = the narrative outcome (e.g. `🎯 Marv Successfully coordinated an attack against Avery Xavier with Frankie, Wilson`)
- `die1` / `die2` / `amod` / `smod` / `cmod` / `total` = the real roll values
- `outcome` = the real roll outcome (`'Success'` / `'Wild Success'` / `'High Insight'`)
- `insight_awarded` = `outcome === 'High Insight'` for PCs

Then suppress the standalone `saveRollToLog` write by adding the label to the `isTrimmedRoll` check in `executeRoll` (`app/stories/[id]/table/page.tsx:5478`). `compactRollSummary` strips the emoji and renders the trim; `▸` expands to the dice breakdown.

Reference implementation: Coordinate-success (commit `<pending>`). Sprint is the older pattern (custom outcome value + bespoke banner); both work, but UNIFIED is preferred when the dice math is interesting and the narrative is short.

**Anti-pattern (do not do):** two rows — one for the dice roll, one for the System effect. The second row has `0+0` dice and reads as a duplicate. Visible bug shipped via the Coordinate flow until 2026-05-10.

**Trim pattern for every new outcome value:**
1. Pick whether the row is Tier A (bespoke banner with its own JSX in `RollsFeed.tsx`) or Tier B (narrative trim via `compactRollSummary`).
2. Tier B: add a branch in `lib/roll-helpers.ts:compactRollSummary` that matches your label / outcome and returns the trimmed sentence. Return `null` falls through to the verbose dice card — only acceptable when the row genuinely has no compact form.
3. Hide the `▸` pip on rows with `die1 = die2 = 0` (auto — handled by `hasRealDice` in `RollEntryCard`). If the row has no real dice, design the narrative to stand on its own.
4. Banned in copy: `(critical)` (use 'Moment of Insight as to why it went so well'), em-dash `—`, en-dash `–`, capital `CDP` (use 'Character Development Points').
5. Wild/HI global tag: ` and has a Moment of Insight as to why it went so well`.
6. LI global tag: ` and has a Moment of Insight as to why it went so badly`.
7. Per-check bespoke overrides (Unarmed HI, Stabilize HI, First Impression HI/LI, Group Check LI) live alongside the general pattern and replace the global tag wholesale.

## Database & Auth
- **Role is now normalized to lowercase**: DB trigger `trg_normalize_role` auto-lowercases `profiles.role` on insert/update. All existing rows backfilled. Always compare against `'thriver'` / `'survivor'` (lowercase). No more `.toLowerCase()` needed — but harmless if left in.
- **Supabase email-confirmation links use `verifyOtp`, not `exchangeCodeForSession`**: confirmation emails carry `?token_hash=<...>&type=signup`, not `?code=<...>`. The latter is for OAuth/PKCE. A `/auth/callback` route built only for `code=` silently fails on every signup-confirmation click. Branch on which params are present and call the right API. Cost: an end-to-end signup test on 2026-05-08C produced "Invalid login credentials" because email never got marked confirmed.
- **Postgres grants `EXECUTE` to `PUBLIC` by default on every new function**: writing `GRANT EXECUTE ON FUNCTION foo() TO authenticated` is a no-op for security purposes — `anon` already had it via PUBLIC. To restrict: `REVOKE EXECUTE ... FROM PUBLIC, anon` first, then GRANT. Surfaced 2026-05-08C when Supabase linter flagged `admin_users_with_login` as anon-callable despite the grant.
- **Trigger functions don't need RPC EXECUTE permissions**: triggers fire from DB events and run as the function owner. Revoking EXECUTE FROM `public, anon, authenticated` on every trigger function in `public` is safe defense-in-depth and clears ~30 linter warnings in one shot. See `sql/security-hardening-2026-05-08.sql` Tier 2.2.
- **FK to `auth.users` defaults to `NO ACTION` if you don't specify ON DELETE**: meaning every `DELETE FROM auth.users` errors with FK violations on un-cascaded child tables. The whole DELETE rolls back atomically — partial deletes don't happen. Fix: audit every FK to `auth.users`, set ON DELETE CASCADE for owned data, ON DELETE SET NULL for community-contributed content (where row should persist with attribution cleared). See `sql/fix-auth-cascades-2026-05-08.sql` for the canonical 5-table fix.
- **`information_schema.constraint_column_usage` can hide cross-schema FKs**: the view sometimes doesn't surface FKs from `public.X` to `auth.users` even when they exist. For reliable FK introspection, query `pg_catalog.pg_constraint` directly (`pg_class`, `pg_namespace` joins). Burned ~10 minutes during the cascade audit.
- **Wix DNS doesn't support MX records on subdomains**: even when MX on root works fine. Resend's verification needs an MX on the sending subdomain (`send.example.com`) and Wix returns "this isn't supported" silently. Plan B: migrate DNS to Cloudflare (free, ~30 min). Cloudflare auto-imports existing Wix records before the swap; site stays up if all subdomains were registered (gotcha: Cloudflare's auto-scan can miss `thetapestry.distemperverse.com` style Vercel subdomains — verify the imported list before changing nameservers at the registrar).
- **RLS blocks everything by default**: When creating new tables, always add RLS policies immediately. Storage buckets need separate policies on `storage.objects` — the bucket existing is not enough.
- **Supabase Storage buckets must be created manually**: They don't auto-create from code. Each bucket needs INSERT/SELECT/DELETE policies on `storage.objects` filtered by `bucket_id`.
- **Column must exist before code references it**: Always provide the ALTER TABLE SQL alongside the commit. Don't assume the user has run previous SQL.
- **Every ALTER TABLE migration must end with `NOTIFY pgrst, 'reload schema';`**: PostgREST caches its schema introspection. If the cache predates the column, the API silently strips that column from write payloads — direct DB queries succeed, client updates "revert" on next read. Cost a debug session on 2026-05-04 (pin sort_order revert). Idempotent and cheap; add it unconditionally to every column-add migration.
- **Always `.select()` after `.update()` and check the error**: Fire-and-forget updates with optimistic local state hide RLS rejections, schema-cache misses, and constraint violations. Pattern: `const { data, error } = await supabase.from(t).update(u).eq('id', id).select().maybeSingle()`. If `error` or `!data`, alert and abort — don't repaint.

- **Null-coalescing chains can create false positives**: `npc.wp_current ?? npc.wp_max ?? 10` evaluates to `0` (and filters as "dead") when both fields are null. Only filter entities as dead when their health field has been explicitly set to 0, not when it's null/uninitialized. Use `npc.wp_current != null && npc.wp_current <= 0` instead.
- **Realtime subscriptions must match the events you need**: Subscribing to `INSERT` only means `DELETE` events are invisible to other clients. If a feature clears data (like session end deleting logs), use `event: '*'` so all clients see the change.

## React & Next.js
- **Emoji icons don't respond to CSS `color`**: Emojis render as images. Use SVG icons if you need color to change dynamically (e.g., notification bell).
- **`await` your Supabase calls**: Fire-and-forget (`supabase.from(...).update(...)` without `await`) causes race conditions. The Realtime subscription can fire before the write completes, reading stale data.
- **Optimistic state updates prevent stale reads**: When updating a value (like insight dice), update the local state immediately in addition to the DB write. Don't rely solely on Realtime to propagate changes.

## Conventions

- **Architectural fitness functions = ratchets, not staged-file scans (2026-05-22, grand re-arch Phase 1c).** The existing `check-*.mjs` guardrails scan STAGED files for a banned pattern. Architecture conformance is different: scan the WHOLE repo, compare to a committed baseline (`tasks/_baselines/arch.json`), and fail ONLY on regression (a number moving the wrong way). `scripts/check-arch.mjs` does three: LOC ceilings (god-components shrink only), seam leakage (`.from(` outside `lib/data/**`, `.channel(` outside `lib/realtime/**`), prod console (`console.log|warn` in app/components/lib). Re-baseline DOWN with `--save` after an improvement; `--save` refuses to RAISE a number without `--force`. This turns "migrate 1,324 call sites" from an aspiration into a CI-enforced monotonic decrease. Verify the FAIL path when you build a ratchet (lower a baseline by 1, confirm exit 1) - a ratchet that can't block is theatre.
- **Type a seam LOCALLY to avoid a big-bang global typing migration (2026-05-22, Phase 1b).** `lib/supabase-browser.ts`'s client is NOT parameterised with `<Database>`, so all 1,324 inline `.from()` return `any`. Parameterising it globally would surface tsc errors across 98 files at once - not a "pure addition." Instead `lib/data/db.ts` casts the client to `SupabaseClient<Database>` LOCALLY, so repositories get full typing while the rest of the app is untouched until it migrates. Remove the local cast + parameterise globally only once every consumer is on the seam.
- **Mechanical `.from` migration: only UNIFORM operations are cleanly mechanical (2026-05-22, Phase 3).** A repo migration is a safe behavior-preserving string-replace ONLY when many call sites share ONE query shape: build a named repo fn returning the typed `{data,error}` builder (e.g. `getCampaignNpcs(id)` = `.from('campaign_npcs').select('*').eq('campaign_id',id)`, `insertRollLog(rows)`), then prefix-replace `supabase.from('X').op(` -> `repoFn(` so the trailing args + chain (`.eq`, `.select`, `.order`, Promise.all element) are preserved untouched. This took table-page + repo-wide leakage 1324->1266 with zero behavior change. What does NOT migrate cleanly: (1) VARIED writes - `.update(patch).eq('id',x)` with a different patch per site needs per-site arg-reordering (transcription-risky) OR a thin accessor that doesn't really encapsulate (ratchet-gaming); (2) trunk-table queries (initiative_order/character_states/scene_tokens) - migrating them now then rebuilding into useInitiative/useTacticalSync/useRollResolution is double-handling, so they migrate WITH their hook. Writes use a loose payload param (`rows: any`) during migration - the typed-payload tightening is a separate pass (one roll_log site stuffs a DamageResult into a Json column; strict typing surfaced it - logged, deferred to the rebuild). Don't force every `.from` onto a thin wrapper just to drop the ratchet number; that's churn the hook rebuild redoes.
- **Stale-closure-safe realtime hook: deps `[campaignId]` + handlers in a ref (2026-05-22, Phase 1a).** The recurring "one client stops seeing the other" bug comes from channel effects whose dep array includes state/setters, so the channel tears down + resubscribes on unrelated renders. `useCampaignChannel` fixes it structurally: the effect deps are `[campaignId]` ONLY (subscribe once per campaign), and the subscribed callbacks read the latest handler from a ref that's mirrored every render - so you get current closures over current state WITHOUT resubscribing. Plus every handler is auto-wrapped with the Sentry guard (100% coverage vs the old opt-in). This is the pattern every realtime consumer migrates onto in Phase 3.

- **Terminology: the GM has no PCs (locked 2026-05-22).** A **PC** is a Player Character (player-controlled). An **NPC** is a Non-Player Character (GM-controlled). The GM controls NPCs only. NEVER write "GM's PC" or "GM PC" in docs, UI copy, or comments - it's a category error; the GM-controlled combatant is an NPC. Caveat: "**non-GM PC**" is CORRECT and stays - it means a PC controlled by a non-GM user (a player's character), used in RLS/permission contexts.
- **"new window time?" = handoff prompt**: When the user asks `new window time?`, respond with a concise, self-contained prompt they can paste into a new chat to resume. Shape: `I want to <task>. Load <relevant spec files> first.` Should reference the project-surviving files (tasks/todo.md, tasks/spec-*.md, tasks/rules-extract-*.md, tasks/testplan.md, tasks/lessons.md) so fresh-me has everything needed without re-litigating the last session. Load tasks/spec-communities.md and tasks/rules-extract-communities.md first.` Don't include stuff only meaningful in the current session (recent commit hashes, "we just shipped X"); stick to things fresh-me can actually reload.
